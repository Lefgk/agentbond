## 3. Findings

### [M-1] Instant `setArbiter` lets the operator skip the withdraw cooldown and drain the bond in one block. **Fixed**

**Where:** `setArbiter` (main L182-190), `resolveClaim` L262-293.
**Impact:** With no open claims, the controller could set the arbiter to a puppet, file a claim from an alt address and have the puppet slash 100% of the bond to that alt in the same block. That bypasses the 7-day withdraw cooldown, which exists so claimants can file before coverage leaves. An operator who sees trouble coming exits before anyone can claim, so the advertised coverage is worthless. The ERC-8004 *agent wallet* (a hot key the AI agent itself holds) had the same power.
**PoC:** `test_poc_arbiterSwapBypassesCooldown` passed on `main` (alt got 1,000 USDC in one block).
**Fix:** `setArbiter` now only queues a change (`pendingArbiter`), owner-only (8004 owner or the account; not the agent wallet). `applyArbiter` finalises it after `withdrawCooldown` and only with no open claims, so claims filed during the delay are judged by the old arbiter. Passing the current arbiter cancels a queued change.
**Tests:** `test_M1_arbiterSwapNoLongerBypassesCooldown`, `test_M1_ownerCanCancelQueuedArbiter_andWalletCannotQueue`, invariant `invariant_noInstantArbiterSwap`.

### [M-2] Anyone can create someone else's bond and choose its arbiter (key squatting). **Fixed**

**Where:** `_deposit` L380-404 (first deposit names the arbiter, no caller check).
**Impact:** An attacker deposits 1 wei for a victim's agent id or address with an arbiter they control. The victim's own deposit then reverts with `ArbiterMismatch`. Their `setArbiter` could be blocked with a free spam claim (M-3), and any top-up the victim made with `arbiter = 0` landed under the attacker's arbiter and could be slashed to the attacker. The result is a permanent DoS of a victim's bond key and possible theft of top-ups.
**PoC:** `test_poc_bondKeySquatting` passed on `main` (attacker's alt got the victim's 1,000 USDC top-up).
**Fix:** creating a bond (first deposit, which names the arbiter) now requires the bond controller (8004 owner/agent wallet, or the account). Anyone can still top up an existing bond.
**Tests:** `test_M2_onlyControllerCanCreateBond`, invariant `invariant_noSquat`.

### [M-3] Free claims can keep `openClaims > 0` forever and lock withdrawals. **Fixed**

**Where:** `fileClaim` L235-258; `requestWithdraw`/`withdraw`/`setArbiter` all require `openClaims == 0`.
**Impact:** Filing a claim cost only gas (fractions of a cent on Base). Anyone could keep one claim open at all times, re-filing after each rejection or 14-day expiry, so the operator could never withdraw (or rotate the arbiter). Funds were locked indefinitely at near-zero attacker cost.
**PoC:** `test_poc_freeClaimSpamLocksWithdraw` passed on `main` (5 rounds, attacker spent 0 USDC).
**Fix:** new immutable `claimDeposit` (constructor arg #5; `DeployConfig.CLAIM_DEPOSIT = 1 USDC`). Each claim escrows it. It is **refunded** on a slash or an expiry (the arbiter's silence is not the claimant's fault) and **added to the bond** on a rejection or a cancel (so a spammer can't dodge a rejection by cancelling). The new `heldClaimDeposits` tracks escrowed deposits. Web: "Approve deposit + file claim".
**Tests:** `test_M3_claimSpamCostsDeposit`, `test_M3_depositRefundedOnSlashAndExpiry`, `testFuzz_M3_balanceCoversBondsAndDeposits`, invariant `invariant_heldDepositsMatchPendingClaims`; balance invariant now `balance == Σ bond.amount + heldClaimDeposits`.
**Residual:** an operator whose arbiter never acts can still be blocked for 14 days per spam claim, at 1 USDC of capital per claim. Pick a responsive arbiter.

### [L-1] ERC-8004 registry is an upgradeable proxy owned by an EOA. Acknowledged
`0x8004A169…a432` on Base has EIP-1967 implementation `0x7274…9c02` and `owner()` = `0x5472…2603`, which has no code (an EOA). Whoever controls that key can upgrade the registry so `ownerOf` returns any address, then queue and withdraw every agent-keyed bond after the 7-day cooldown, or change arbiters. This is a trust assumption on the ERC-8004 team. Watch for `Upgraded` events; address-keyed bonds are not affected.

### [L-2] A burned or unminted agent leaves its bond stuck. Acknowledged
If `ownerOf(agentId)` reverts, `_isController`/`_isOwner` return false, so nobody can withdraw or change the arbiter. Claims can still be slashed. Only the owner's own action (burn) triggers it.

### [L-3] USDC blacklist blocks payouts to a blacklisted party. Acknowledged
`withdraw` pays `_operator(b)`. A blacklisted account-keyed operator can't withdraw; an agent owner can transfer the NFT and withdraw to the new owner. `resolveClaim` and `expireClaim` revert if the claimant is blacklisted; the arbiter can still reject (slash 0) to clear the claim. A pull-payment pattern would remove this; not worth the complexity for v1.

### [L-4] A queued arbiter change survives an agent NFT transfer. Acknowledged
`pendingArbiter` isn't cleared when the 8004 NFT changes hands. The new owner should call `setArbiter(key, currentArbiter)` to cancel anything the previous owner queued (they are the only one who can apply it, since `applyArbiter` is owner-only).

### [I-1] Arbiter is fully trusted
An arbiter can slash up to the remaining bond to any claimant, or reject everything. A bond whose arbiter is the operator (or an alt) is worthless. The UI/consumers should flag `arbiter == operator`; alt addresses can't be detected on-chain.

### [I-2] A controller can still claim through an alt address
`ControllerCannotClaim` is trivially bypassed with another address. Harmless: the arbiter decides, and after M-1 the arbiter can't be swapped instantly.

### [I-3] `requested` is not capped to the bond
Claims may request more than the bond; slashes are capped at `min(requested, remaining)`. Display-only concern.

### [I-4] No reentrancy surface
USDC has no transfer hooks; all external calls follow state updates; `nonReentrant` is on every function that transfers. `fileClaim` and `expireClaim` gained `nonReentrant` because they now move USDC.
